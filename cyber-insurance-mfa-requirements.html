Cyber insurance MFA requirements: which accounts insurers expect it on

By William Todd, IT support and cybersecurity engineer · Updated 2026-11-21

Most cyber insurers now expect multi-factor authentication (MFA) on five things: email for every user, all remote access, admin accounts, backups, and the cloud apps that hold sensitive data. Exact wording differs by insurer and application, so read yours line by line, but if you cover these five you can answer most MFA questions with a confident "yes".

This matters more than the premium. If you answer "yes" to MFA and an incident shows it wasn't actually enforced, an insurer may dispute the claim based on what you put on the application. "Partly" isn't "yes".

The 5 areas insurers ask about

AreaWhat "yes" meansCommon gap
1. EmailMFA enforced for every mailbox user, including the owner, part-timers and shared loginsThe owner or one "special" account was exempted
2. Remote accessMFA on VPN, remote desktop, remote-support tools and any web portal into your networkRDP open to the internet, or a vendor's remote tool with a shared password
3. Admin / privileged accountsMFA on Microsoft 365 or Google Workspace admins, domain admins, firewall and router admin, and your MSP's accountsAn old "admin" account nobody uses, still active without MFA
4. BackupsMFA on the backup console and cloud backup account, so an attacker can't delete themBackup portal on a password only, often the same one as email
5. Cloud apps with sensitive dataMFA on accounting, payroll, banking, practice management, CRM and file sharingApps that use their own login instead of single sign-on

Some applications also ask whether MFA covers all users or only admins, and whether it applies to "internal" network access. Answer what's true for your environment and add a note if the form allows it.

Which MFA methods count

  • Authenticator app with number matching or push (Microsoft Authenticator, Google Authenticator, Duo and similar). Accepted almost everywhere and free.
  • Security keys and passkeys (FIDO2). Phishing-resistant and the strongest option. Some insurers ask about phishing-resistant MFA specifically, especially for admins.
  • SMS or phone call codes. Better than nothing, but some insurers and security frameworks treat them as weaker. Avoid them for admin accounts.
  • Not MFA: a second password, security questions, or "remember this device" for months with no re-check.

How to turn it on (free, built in)

  • Microsoft 365: in the Microsoft Entra admin center, turn on Security defaults (free on every tenant) or, if you have Entra ID P1 (included in Microsoft 365 Business Premium), use Conditional Access policies requiring MFA for all users. Then check the per-user MFA report for anyone not registered.
  • Google Workspace: Admin console → Security → Authentication → 2-Step Verification. Allow users to turn it on, give them a deadline, then switch enforcement on.
  • Everything else: list every app staff sign in to (the onboarding inventory helps) and turn on each app's MFA, or connect it to Microsoft or Google sign-in so one MFA policy covers it.

Admin menus move often. If a path above has changed, search the vendor's help for "require MFA for all users". For a staged rollout plan and staff email template, see the MFA rollout plan.

Prove it: the evidence to save

Before you sign the application, save these in a dated folder. They're what an underwriter or claims adjuster may ask for:

  1. A screenshot of the policy that enforces MFA (Security defaults, Conditional Access or Google enforcement) showing it's on for all users.
  2. An MFA registration report showing every active user enrolled.
  3. A list of exceptions, each with the reason, an owner and an end date. Ideally the list is empty.
  4. Screenshots of MFA settings for the VPN or remote tool, the backup console and the key cloud apps.
  5. Your written password and MFA policy.

Re-check before every renewal. Accounts get added, and exceptions made "for a week" tend to become permanent. The renewal checklist walks through the rest of the application.

Common mistakes that turn a "yes" into a denied claim

  • Exempting the owner. Executives are the most-targeted accounts.
  • Forgetting service and shared accounts. A shared front-desk mailbox without MFA is still email without MFA.
  • Legacy sign-in left on. Old email protocols (IMAP, POP, basic authentication) can bypass MFA. Make sure they're blocked.
  • The MSP's own access. If your IT provider signs in to your systems, their accounts need MFA too. Ask them to confirm in writing.
  • Answering for the plan, not the reality. "We're rolling it out next month" is a "no" today. Say so, or finish the rollout before you sign.

Frequently asked questions

Do all cyber insurers require MFA?

Not every insurer has the same rule, but MFA is now a standard underwriting question, and many insurers make it a condition of coverage or pricing, especially for email, remote access and admin accounts. Check your own application wording.

Does SMS count as MFA for cyber insurance?

Usually yes, but some insurers and security frameworks treat SMS as weaker than an authenticator app or security key. Use an app or security key at least for admin accounts.

What happens if I say I have MFA and I don't?

Misstatements on an application can give an insurer grounds to dispute or deny a claim. Answer accurately, and if MFA isn't fully enforced yet, finish the rollout before signing or disclose the gap.

Do I need MFA on backups for cyber insurance?

Many insurers ask about protecting backups, and MFA on the backup console is one of the most effective controls, since ransomware groups try to delete backups first.
