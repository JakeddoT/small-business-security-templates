Backup restore test checklist

By William Todd, IT support and cybersecurity engineer · Updated 2026-11-21

To test backups in a small business, restore a real sample of your data (a folder, a mailbox and, once a year, a whole computer) to a separate location, confirm the files open and are current, and record the result in a backup test log. The checklist and sample log below cover what insurers commonly ask to see; a quarterly test usually takes under an hour.

A backup you have never restored is a hope, not a plan. Most failed restores come from problems a test would have caught months earlier: a job that silently stopped, a drive that filled up, or a password nobody remembers.

Backup restore test checklist (10 steps)

  1. List what must be recoverable. File shares, email, accounting data, line-of-business databases, and at least one laptop or workstation.
  2. Check the backup job history first. Confirm the last several jobs succeeded and the newest copy is as recent as you expect.
  3. Pick a representative sample. A folder of recent work files, one mailbox, and a file that changed this week (so you can prove the copy is current).
  4. Restore to an isolated location, such as a new folder, a spare PC or a test VM. Never restore over live data.
  5. Open several files of different types (documents, spreadsheets, PDFs, a database export) and confirm they are intact.
  6. Time the restore from start to usable data. Compare it with how long the business can actually be down.
  7. Test the offline or immutable copy, not only the convenient one. Ransomware targets the backups it can reach.
  8. Once a year, restore a whole machine (image or bare-metal restore), not just files.
  9. Have a second person run the restore from your written steps, so recovery does not depend on one IT person.
  10. Record the result in the backup test log, fix any problem, and retest the failed item.

How often to test backups

WhatTest typeSuggested frequency
Files and shared foldersRestore a sample folderQuarterly (monthly if data changes constantly)

Offline or immutable copyRestore from that copy specificallyAt least twice a year

Treat these as sensible starting points, not a rule. If your insurer, a contract or a regulator sets a schedule, follow theirs.

Questions your test should answer

  • Is at least one copy offline or immutable, out of ransomware's reach?
  • How old is the newest good copy, and how much work would you lose?
  • Could we restore a whole computer, not just files?
  • How long would the restore take, and can the business wait that long?
  • Who knows how to run a restore if your usual IT person is unavailable?

Common mistakes

  • Trusting the green checkmark. A "successful" job can still back up the wrong folders or skip locked files. Only a restore proves it.
  • Treating sync as backup. OneDrive, Dropbox or Google Drive sync can copy encrypted or deleted files to every device. Version history and recycle bins help, but check that you also have a separate backup you can restore from.
  • Using the same admin accounts for backups and the network. If an attacker gets those credentials, they can often delete the backups too.
  • Never testing the offsite copy because it is slow. That is the copy you will need after a fire or ransomware.

Frequently asked questions

How often should backups be tested?

Run a file-level restore test at least quarterly, a full system or server restore at least once a year, and an extra test after any change to your backup software, storage or schedule.

How do I test backups in a small business without an IT department?

Pick one folder and one mailbox, restore them to a new location, open several files, and write down the date, what you restored, how long it took and whether it worked. Rotate who runs the test so more than one person knows how.

What should a backup test log include?

Date, system or data tested, backup date restored from, restore location, time taken, result (pass or fail), issues found, fix applied and the tester's name. Keep a year of entries so you can show a history.

What is an immutable backup?

A backup copy that cannot be changed or deleted for a set period, which protects it from ransomware and from an attacker using stolen admin credentials.
